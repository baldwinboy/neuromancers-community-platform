# Daily.co

Daily is the alternative meeting provider
(`IntegrationSettings.meeting_provider = daily`). The vendored client is in
`daily/`, generated by clientele from the upstream spec.

## Client regeneration

The Daily client is generated from `https://docs.daily.co/openapi.json`:

```sh
uv run clientele start-api -u https://docs.daily.co/openapi.json -o daily --regen
```

After regeneration, apply the compatibility patch documented in
`daily/MANIFEST.md` (clientele 2.3.1 emits a non-`Literal` discriminator that
pydantic 2.13 rejects at import; replace the annotated union in `daily/schemas.py`
with a plain union).

## Rooms

`DailyProvider.create_room` creates a **private** room with `nbf` at the session
start and `exp` at the session end plus a one-hour grace period. Room names are
sanitised to Daily's allowed character set with a unique suffix.

## Join links

`DailyProvider.join_url` creates a meeting token (`POST /meeting-tokens`) with
`room_name`, `user_id` (our user pk), `user_name`, `is_owner` (host vs guest),
`nbf` and `exp`, then returns `room_url?t=<token>`. Tokens are short-lived and
bound to the join window, so a copied link is not reusable outside it.

## Webhooks

`POST /webhooks/daily/` with the `X-Webhook-Signature` HMAC-SHA256 header and
`IntegrationSettings.daily_webhook_secret`. The handler accepts `payload` (or
top-level) fields, maps `room`/`room_name`/`roomName` to `provider_room_id`, and
records minutes from `start_ts`/`end_ts` (or `duration`) and attendance from
`participant.is_owner`/`role`.

Processing is idempotent. Exact upstream field/header names are `UNVERIFIED`
until a live webhook is observed; the parser tolerates variants.
